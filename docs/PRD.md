## 1. 제품 개요와 가설

최신 플랫폼 결정: PC·태블릿·모바일의 웹 브라우저에서 URL로 접속하는 공동생활 웹게임으로 먼저 개발한다. 이 채팅에서는 기획과 Codex 전달 자료를 정리하고, 실제 구현은 Codex에서 진행한다. 가족 초대·참여·공유 저장 요구를 유지하며 단독 플레이 게임으로 축소하지 않는다.

함께 사는 사람들과 반려동물이 작은 도트 세계에서 생활하고, 사용자는 공간과 캐릭터를 통해 서로의 상태와 공동생활 정보를 확인한다. 집을 중심으로 직장·학교·밖을 오가며 다른 구성원의 화면을 볼 수 있다.

핵심 경험 가설은 '구경하고 싶어서 열고, 함께 사는 데 도움이 되어 계속 사용하는 서비스'이다. 차별화 가설은 실제 구성원과 반려동물의 개성, 캐릭터의 자율 행동, 생활 이벤트, 공유 가능한 장면의 결합이다. 시장 반응과 지불 의사는 아직 검증하지 않았다.

초기 대상 제안: 함께 사는 성인 2명과 반려동물이 있는 가구부터 검증한다. 이는 검증 대상의 제안일 뿐 서비스 인원을 2명으로 고정하는 정책이 아니다. 1인 가구와 반려동물 0마리도 자연스럽게 시작하도록 설계한다.

## 3. 최초 설정과 참여 흐름

1. Google 로그인 후 집 이름을 입력한다.
2. 대표 본인의 이름과 v1:HTBA 외형을 설정한다.
3. 집은 대표 1명·반려동물 0마리로 생성되고 바로 게임에 들어간다.
4. 대표는 필요할 때 가족 초대 링크를 발급한다. 가족은 인증과 명시적 수락 후에만 추가된다.
5. 서로 다른 유효한 초대는 동시에 수락할 수 있다. 같은 초대는 한 계정만 사용하며 같은 계정의 재시도는 멱등이다.
6. 반려동물은 입장 후 대표가 이름·고양이/강아지를 한 마리씩 등록·수정한다. 모든 활성 가족이 조회한다.
7. 재로그인과 오프라인 상태에도 가입·캐릭터·반려동물을 유지한다.

공식 인증 확정안: Google OIDC 로그인 + 초대 링크를 사용한다. 로그인 제공자와 가구 초대는 역할이 다르며, 로그인만으로 임의의 집에 가입되는 구조를 만들지 않는다. Google OIDC 로그인 실제 연결은 Google Cloud Redirect URI·인증 정보 설정 후 별도로 검증한다.

| 상태 | 세계와 얼굴 목록 | 비고 |
|---|---|---|
| 초대 대기 | 표시하지 않음 | 가족 인원은 실제 Membership로 계산 |
| 링크 열람, 참여 미수락 | 표시하지 않음 | 페이지를 열었다는 이유만으로 입주 처리하지 않음 |
| 인증 및 참여 수락 완료 | 표시 | 서버에서 가입이 확정된 구성원 |
| 가입 후 브라우저 종료·오프라인 | 표시 유지 | 가입 상태와 접속 상태를 분리하는 설계 제안 |
| 초대 만료·취소 | 미가입 사람은 표시하지 않음 | 실제 참여가 없는 경우 |

계획 인원 정책은 제거했다. 가입 인원은 실제 Membership 목록에서 계산한다. 구성원 탈퇴·제거·대표 권한 이전과 기존 기록의 처리는 별도 정책으로 정해야 한다. 미성년자·비사용 가족의 대리 프로필 정책은 미정이며, 현재는 미참여자 미표시 요구를 우선한다.

## 5. 자율 행동과 현실 정보

자율 행동 제안: 집에서는 소파에 앉기·냉장고 보기·창밖 보기·반려동물 곁에 머물기, 직장에서는 타이핑·커피·스트레칭. 반려동물은 방석에서 쉬거나 구성원을 따라다닌다. 성격과 시간·장소에 따른 규칙 및 확률로 시작하고 AI 대화 모델은 필수로 두지 않는다.

| 정보 | 신뢰 기준 |
|---|---|
| 실제 장소·귀가 상태 | 사용자 설정 또는 동의한 실제 연동 결과; 갱신 시점 표시 |
| 실제 기분·먹고 싶은 음식 | 본인이 선택해 공유한 정보 |
| 화면 속 걷기·쉬기·냉장고 보기 | 캐릭터의 가상 연출 |
| 식료품 사용·급여·산책 완료 | 실제 수행 후 사용자가 기록하거나 신뢰할 수 있는 연동으로 확인 |
| 가전 작동 완료 | 실제 기기 상태로 확인 |

캐릭터의 자율 연출은 실제 재고 차감, 돌봄 완료, 다른 사람 명의의 메시지, 가전 제어를 직접 실행하지 않는다. 브라우저를 닫은 동안에는 시간과 상태를 저장하고 재진입 시 장면을 재구성할 수 있다. 모든 캐릭터를 서버에서 매 프레임 시뮬레이션할 필요는 없다.

## 6. 생활 기능 상세 제안

- 말풍선: 음식·기분·가벼운 요청을 선택형으로 입력하고 필요할 때 자유 입력한다. 유지 시간과 해제 기능으로 오래된 기분을 현재 감정처럼 남기지 않는다.
- 반응: 좋아, 내가 살게, 쉬고 있어 등 짧은 상호작용. 관찰 중인 사람의 계정으로 실행하지 않는다.
- 식료품: 이름, 보관 위치, 수량 또는 남은 정도, 선택적 소비기한, 마지막 확인 시점. 정확한 개수와 '많음/조금/없음'을 식품 특성에 맞게 지원한다.
- 장보기: 음식 제안에서 부족한 재료를 추가하고 담당자를 표시한다. 식료품을 읽고 수정할 수 있는 가구 범위를 서버에서 검증한다.
- 반려동물: 등록된 수와 외형을 반영하고, 밥·산책 기록의 작성자와 시간을 확인할 수 있게 한다. 가상 허기와 실제 반려동물의 상태를 동일하게 취급하지 않는다.
- 알림: 퇴근·귀가, 명시적 요청, 택배, 가전 완료 등 생활 사건 중심. 종류별 설정, 조용한 시간, 중복 방지와 앱 내 이력을 검토한다.
- 배송: 초기 수동 기록과 향후 배송 API를 구분한다. 다른 앱 알림을 자동으로 읽을 수 있다고 가정하지 않는다.
- IoT: 처음에는 한 플랫폼의 한 기기 상태 반영을 검증한다. 명령 접수와 작동 완료를 구분하고 자율 캐릭터 행동이 실물 장치를 조작하지 않게 한다.

| 환영 선물과 입주 연출 | 초대한 사람이 준비한 메시지·가구, 여행 가방을 들고 입주 | 초대 수락 동기와 첫 감정 경험 |
| 우리 집 도트 극장 | 자율 행동을 세 컷이나 짧은 영상으로 구성 | 공유할 가상 에피소드; 실제 사실 기록과 명확히 구분 |
| 한 번의 터치로 배려 보내기 | 응원 커피, 잘 자 별, 내가 살게·산책할게 | 낮은 입력 부담과 반복 방문 |
| 귀가할 때 살아나는 집 | 귀가 상태 변경에 현관·가족·반려동물 반응 | 수동 상태만으로도 즐거운지 검증 |
| 태블릿 액자 모드 | 집을 크게 켜두고 생활 장면을 관찰 | 가정 내 상시 관찰 용도; 기기 성능·전력도 확인 |
| 사진 기반 도트 외형 초안 | 업로드 사진을 바탕으로 외형을 제안하고 수정 | 제작 난도·권리·품질·비용 검증 후 확장 |
| 집 꾸미기·생활 기념품 | 함께 쌓은 기록을 집의 오브제로 표현 | 장기 애착, 테마·외형 수익화 가능성 |

공유는 사용자가 선택한 장면만 대상으로 하고 기본 공개 범위에서 실제 위치·귀가 시간·개인 말풍선을 제외한다. 외부 사진/영상 링크와 집 입장 권한을 분리한다. 공유되는 구성원의 표현과 공개 범위는 본인의 선택을 존중한다.

경쟁 참고: SumOne의 공동 캐릭터·인테리어·기분 공유, Widgetable의 공동 반려동물·상태 공유가 이미 존재한다. 따라서 '귀여운 캐릭터 + 기분 공유'만으로 차별성을 입증하지 못한다. 실제 우리 가족이 살아가는 공간과 연출·생활 기능의 결합을 제품 가설로 검증한다.

## 8. 기술·플랫폼 선정

대상은 PC·태블릿·모바일 반응형 웹 브라우저다. 설치 없이 HTTPS URL로 접속하며 Google OIDC 로그인과 초대 링크로 참여한다. 기존 모바일 우선 PWA·Capacitor 계획을 대체한다.

선정안: React + TypeScript + Vite + Phaser / Java 21 + Spring Boot / MySQL + JPA + Flyway / REST + WebSocket(STOMP). React·Phaser·Spring·MySQL은 이미 웹에 적합하므로 유지한다. 실시간은 양방향 장면 상호작용을 고려해 SSE 중심 안에서 WebSocket으로 변경한다. 상세 근거는 TECH_STACK, 계약과 구현 순서는 IMPLEMENTATION을 따른다.

가족 초대·인증·공유 저장은 웹 MVP에 포함한다. 브라우저 localStorage만으로 공유 서비스를 대체하지 않는다. 첫 그래픽 시제품만 임시 데이터로 검증할 수 있다.

PWA 설치·Capacitor·네이티브 앱·앱스토어·브라우저 종료 후 지속 위치 추적은 현재 구현 범위가 아니다. 초기 장소와 퇴근·귀가·택배 사건은 사용자가 명시적으로 기록한다. 웹 내 알림과 저장된 이력을 먼저 구현하고 Web Push는 별도 후속 기능으로 둔다. IoT·배송 API는 실제 제공자 검증 후 웹 서버 연동으로 확장한다.

## 9. 그래픽 적용 방침

사용자는 기존 데모 그래픽이 생각한 방향과 거리가 멀다고 밝혔다. 기존 HTML의 사각형 기반 픽셀 그림·색·캐릭터 비율을 목표 디자인으로 사용하지 않는다.

권고 순서는 '기본 UX 규칙 정리 → 아트 방향 시안 → 목표 품질의 집 화면 1개 → 기능 개발과 실제 자산 통합 → 다른 공간 확장 → 최종 연출·성능 점검'이다. 그래픽은 마지막에 일괄 교체하는 작업으로 미루지 않는다. 구체적인 색감·도트 밀도·캐릭터 비율은 아직 결정되지 않았다. ART_DIRECTION 문서에 산출물과 판단 기준을 기록한다.

## 10. 웹 MVP 개발 범위

| 단계 | 내용 | 완료 의미 |
|---|---|---|
| M0 | 웹 기반·아트 시안·움직이는 집 | 그래픽·React/Phaser·이동·가구·말풍선·반응형 입력 검증; 임시 데이터 시제품 |
| M1 | 실제 계정·집 생성·초대·DB | 두 계정의 수락 후 등장·재접속 유지·가구 권한 검증 |
| M2 | 실시간 공동 공간·얼굴 관찰·자율 행동 | 집·직장·학교·밖의 기본 장면, WebSocket 동기화·복구 |
| M3 | 기분·음식·생각·식료품·수동 사건·웹 내 알림 | 서버 저장·가구 공유·브라우저 검증. M0~M3가 웹 MVP |
| M4 | 사진·환영·꾸미기·Web Push·배송/IoT | 필요와 실제 연동 검증에 따른 확장; 네이티브 앱은 별도 결정 |

M0만 끝낸 결과를 웹게임 전체 완성으로 보고하지 않는다. 사용자 확정 요구에 없는 점수·레벨·강제 퀘스트·임의 가족 NPC를 기본 범위에 추가하지 않는다.

출시 날짜·운영 예산·유료화 금액은 미정이다. 검증 지표는 초대 수락률, 7일 후 가구 내 2인 이상 사용, 자발적 재방문, 생활 기록 유지, 사용자가 선택한 공유 행동이다. 목표 수치는 초기 데이터로 정한다.

## 11. 현재 구현·검증 상태

이번 v0.5 변경은 웹플랫폼 명세와 Codex 전달 자료 수정이다. 실제 웹게임·서버·DB·새 그래픽은 이 작업에서 제작하지 않았다. 아래 검증은 과거 참고 HTML에 대한 범위이며 v0.5 제품 검증 결과가 아니다.

- 현재 산출물은 기획 문서와 서로 분리된 인터랙티브 HTML 모의 화면이다. 통합 제품·운영 저장소·실제 로그인·서버 DB·푸시·IoT는 구현하지 않았다.
- 얼굴 전환 예시는 로그인 구성원과 관찰 구성원의 분리, 상태 변경 주체, 냉장고·돌봄 상호작용을 설명한다. 예시의 자유로운 계정 전환은 실서비스 인증 방식이 아니다.
- 과거 초대 예시는 당시 계획 인원, 반려동물 0마리, 미참여자 미표시, 참여 수락 뒤 등장, 기념사진을 설명한다. 예시의 최대 사람 8명·반려동물 4마리는 화면 데모 범위이며 서비스 제한으로 확정하지 않았다.
- JavaScript 문법과 간이 DOM 환경의 상호작용, Canvas 장면 렌더링을 확인했다. 실제 브라우저 전체 레이아웃, 실제 기기, 접근성·성능·인증·동시성은 검증하지 않았다.
- 그래픽은 사용자가 목표와 다르다고 피드백한 임시안이다. 프로덕션 아트로 재사용하도록 승인받은 것이 아니다.
